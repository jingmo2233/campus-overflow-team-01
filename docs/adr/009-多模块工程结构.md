# ADR-009：多模块工程结构（限界上下文 × 六边形分层）

- **状态**：已接受
- **日期**：2026-10-22
- **决策者**：CampusOverflow 团队（PO / SM / Dev）
- **相关**：ADR-001（模块化单体）、ADR-008（领域与持久化分离）、ArchUnit 适应度函数 FF-1 ~ FF-6

## 背景

CampusOverflow 有 4 个限界上下文（Identity、Q&A、Reputation、Discovery）与 1 个共享内核。
如果只用一个 Maven 模块、靠 `com.campusoverflow.qa.domain` 这类包名区分层次，会出现三个问题：

1. **边界没有物理约束**：应用层可以直接 `import` 另一个上下文的 `domain` 类，编译期不会报错，只能靠人工评审发现；
2. **领域层容易被框架污染**：`domain` 包里的类可以随手加 `@Entity`、`@Service`，单元测试变慢、聚合难以脱离 Spring 运行；
3. **并行开发冲突**：6 个人在同一模块里改代码，构建与测试没有隔离，任何人的红测试都会阻塞所有人。

课程要求（Lab 4）与 ArchUnit 适应度函数（FF-1 ~ FF-6）都要求这些边界**可自动验证**。

## 决策

### 1. 顶层按上下文切分，共 6 个 Maven 模块

```
co-shared-kernel      领域异常、Actor、事件契约、分页等纯 Java 公共件
co-identity           身份与认证（参考实现）
co-qa                 问答核心
co-reputation         声誉与激励
co-discovery          发现（搜索 / 通知）
co-bootstrap          Spring Boot 启动装配（唯一可执行模块）
```

### 2. 每个上下文内部再按六边形分 5 个子模块

```
co-qa/
├── co-qa-api             发布语言：跨上下文查询接口 + 集成事件（无框架依赖）
├── co-qa-domain          聚合、值对象、仓储接口（纯 Java）
├── co-qa-application     用例编排、事务边界、事件发布
├── co-qa-infrastructure  JPA / Redis / JDBC 适配器与迁移脚本
└── co-qa-interfaces      REST 控制器与请求/响应模型
```

4 个上下文 × 5 层 + shared-kernel + bootstrap = **27 个 Maven 模块**。

### 3. 依赖方向（由 Maven 依赖 + ArchUnit 双重强制）

| 模块 | 允许依赖 | 说明 |
| --- | --- | --- |
| `*-api` | `co-shared-kernel` | 发布语言必须稳定、轻量，任何上下文都可安全引用（FF-5） |
| `*-domain` | `co-shared-kernel` | 纯 Java，禁止 Spring / JPA / Jackson（FF-1） |
| `*-application` | 本上下文 `api` + `domain` + 其他上下文 `api` + Spring `context`/`tx` | 事务边界与用例编排（FF-4） |
| `*-infrastructure` | 本上下文 `application` + Spring Data / Redis / CommonMark 等 | 适配器实现，依赖由外向内 |
| `*-interfaces` | 本上下文 `application` + Web / Validation / springdoc | 只做协议转换，不含业务规则 |
| `co-bootstrap` | 全部 `*-interfaces` + `*-infrastructure` | 唯一装配入口，不写业务逻辑 |

### 4. 三条不可协商的规则

1. **跨上下文只经 `*.api` 或集成事件**（FF-2）：Q&A 需要知道「谁管理这门课」时，调用 `identity.api.IdentityApi`，绝不 import `identity.domain`。
2. **领域层零框架依赖**（FF-1）：`co-qa-domain` 的 pom 里只有 shared-kernel 与测试依赖，`mvn -pl co-qa/co-qa-domain test` 可在无 Spring、无数据库的情况下运行。
3. **每个上下文的表必须带自己的前缀**（FF-6）：`id_` / `qa_` / `rep_` / `dis_`，物理隔离数据所有权。

### 5. 强制手段

- **Maven reactor**：模块依赖在编译期生效，跨层引用直接编译失败；
- **ArchUnit**（`co-bootstrap` 的 `ArchitectureTest`）：FF-1 领域零框架、FF-2 跨上下文只经 api、FF-3 无环、FF-4 分层方向、FF-5 api 无依赖、FF-6 表名前缀；
- **CI**：`mvn test` 与架构检查在每次 PR 运行。

## 后果

**收益**

- 边界在编译期与 CI 中自动验证，评审只需关注业务规则；
- 每个上下文可独立跑测试（`mvn test -pl co-qa/co-qa-domain -am`，秒级），红测试不会互相阻塞；
- 领域层可在无 Spring 环境下测试，为「先写测试、再写实现」提供基础。

**代价**

- 模块数量多（27 个），首次构建需要下载依赖；单独构建子模块必须带 `-am`（否则找不到同工程的 shared-kernel）；
- 新增一个上下文要复制 5 个 pom 与目录结构，存在模板化的重复；
- 新人需要先理解「依赖只能由外向内」再动手，否则会被 ArchUnit 拦下。

**已知取舍**

- `application` 层允许依赖其他上下文的 `*-api`（如 Q&A 依赖 `identity-api`），这是同步查询的务实选择；异步场景一律走 Outbox 事件；
- `interfaces` 与 `infrastructure` 都只被 `bootstrap` 装配，避免控制器直接 new 仓储。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 单 Maven 模块 + 包分层 | 编译期无边界，跨层引用只能靠 ArchUnit 事后扫描；且 6 人并行时构建与测试无法隔离 |
| 按技术分层（controller / service / repository 各一个模块） | 违背 DDD 的所有权边界，Q&A 的仓储与 Reputation 的仓储被迫同层，跨上下文会自然耦合 |
| 每个上下文一个独立服务（微服务） | 课程场景过度设计：需要服务发现、分布式事务、独立部署；与 ADR-001「模块化单体」冲突 |

## 验证方式

```bash
# 1) 结构可构建（当前 S3 未完成，用 -DskipTests 先验证编译）
mvn -B -f backend/pom.xml clean install -DskipTests

# 2) 架构约束
mvn -B -f backend/pom.xml test -pl co-bootstrap -am \
  '-Dtest=ArchitectureTest' '-DfailIfNoTests=false' '-Dsurefire.failIfNoSpecifiedTests=false'

# 3) 领域层可脱离框架运行
mvn -B -f backend/pom.xml test -pl co-qa/co-qa-domain -am
```

Lab 4 的端到端证明见 `docs/lab4/README.md` 与 `docs/postman/CampusOverflow.postman_collection.json`：
`POST /api/v1/questions` 会依次穿过 `interfaces → application → domain → infrastructure`，链路本身就是分层结构的证据。
