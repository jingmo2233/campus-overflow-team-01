# ADR-010：渐进式质量门禁（Progressive Quality Gates）

- **状态**：已接受
- **日期**：2026-10-26
- **决策者**：CampusOverflow 团队（PO / SM / Dev）
- **相关**：指导书 V2 第 8.2、8.3 节；ADR-009（多模块工程结构）；`docs/错误码.md`
- **编号说明**：指导书 V2 第 8.2 节把本决策称为“ADR-009”，但仓库既有的 009 已被《多模块工程结构》占用。
  为不破坏已有引用（代码注释、PR 讨论、文档链接），本决策顺延为 **ADR-010**；两者内容互不重叠。

## 背景

起始代码里 Q&A 之外的 Reputation / Discovery 还有 142 个 `TODO(S3)` 方法，对应的领域测试在实现完成前必然失败。
实测 `mvn -B test` 在 `co-reputation-domain` 即中止：15 个测试中 1 个 Failure、13 个 Error，根因全部是
`UnsupportedOperationException: TODO(S3)`；即使修掉 Reputation，Discovery 还有 32 个方法未实现。

这带来一个死锁：

1. 分支保护要求“必须通过状态检查”才能合并；
2. CI 跑全量 `mvn test`，在 S0～S2 一定红；
3. 于是**所有 PR 都合不进去**，包括修 CI 的 PR 本身。

如果为此关闭状态检查，CI 就失去意义；如果用 `-Dmaven.test.failure.ignore=true`、`@Disabled`、
删测试或改断言来“变绿”，则触碰指导书 V2 第 9.3 节的学术诚信红线。

## 决策

采用**渐进式质量门禁**：只按 Sprint 范围**缩小必须运行的测试集合**，不改变任何测试的语义。

- 在 `.github/workflows/ci.yml` 的 workflow 级 `env` 中维护 `SPRINT_MODULES`（逗号分隔的 Maven 模块路径）；
- 单元测试与覆盖率门禁使用 `mvn ... -pl "$SPRINT_MODULES" -am`；
- ArchUnit（`ArchitectureTest`）始终对全部模块运行，必须全绿；
- 集成测试（Testcontainers）在 S3 之前 `continue-on-error: true`，S3 起删除该行成为硬门禁；
- 每个 Sprint 计划会后由质量与 DevOps 负责人更新范围，并在 PR 中说明依据。

各 Sprint 的范围（与指导书 8.3 节一致，Q&A 已提前完成故在 S0 即纳入回归保护）：

| Sprint | `SPRINT_MODULES` |
| --- | --- |
| S0 | `co-shared-kernel`、`co-identity/co-identity-domain`、`co-qa/co-qa-domain`、`co-qa/co-qa-application` |
| S1 | 同 S0（Q&A 已纳入；新增边界测试随模块一起跑） |
| S2 | 追加 `co-reputation/co-reputation-domain`、`co-reputation/co-reputation-application` |
| S3 | 删除 `SPRINT_MODULES`，恢复全量 `mvn test` / `mvn verify` |
| S4 | 全量 + 集成测试硬门禁 + 覆盖率 0.80 |

## 红线（不可协商）

- **只能缩小运行范围**。禁止使用 `-Dmaven.test.failure.ignore=true`、`-DskipTests`、`@Disabled`、
  删除测试、修改既有断言来让流水线变绿。
- 每次修改 `ci.yml` 都必须走 PR 评审；教师会检查 `ci.yml` 的提交历史。
- 新增业务规则必须补对应测试；覆盖率只升不降。
- 缩小范围是**临时**措施：S3 必须恢复全量，不能把渐进门禁变成永久豁免。

## 后果

- **正向**：`main` / `develop` 在 S0 起即可保持绿色；PR 的状态检查重新有信号；
  每合并一个 Sprint，门禁范围扩大，质量债务被逐步偿还而不是一次性爆发。
- **代价**：S0～S2 期间 Reputation / Discovery 的回归不会被 CI 捕获，需要靠该上下文主责人本地跑
  `mvn test -pl co-reputation/co-reputation-domain -am`；S2 起这两个模块也进入门禁。
- **风险控制**：S3 计划会必须显式确认“删除 `SPRINT_MODULES`”这一项，否则视为 Sprint 未完成。

## 被否决的替代方案

1. **保持全量测试，等 TODO 全部实现再开 CI**：S0～S2 连续数周红灯，分支保护会阻断所有合并，
   与“每个 Sprint 结束 CI 必须绿”的验收标准直接冲突。
2. **关闭分支保护的状态检查**：失去合并前验证，且违反 7.1.3 节“不允许绕过”的要求。
3. **用 `-Dmaven.test.failure.ignore=true` 让构建返回成功**：构建是绿的，但测试报告仍是红的，
   属于掩盖问题，触碰 9.3 节红线。
4. **为每个模块建独立 workflow**：矩阵配置复杂、状态检查名称不稳定，且无法保证“S3 恢复全量”这一收口动作。
