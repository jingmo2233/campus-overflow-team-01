## 二、团队价值观

按优先级排序，冲突时上位覆盖下位：

1. **能跑通的丑代码，优于跑不通的漂亮设计。** 每周必须有可演示的增量，架构讨论不能成为不交付的理由。
2. **边界靠自动化守，不靠自觉。** 模块依赖、分层、错误码格式这些约定，写成测试（ArchUnit）和检查脚本，不写在文档里等人记。
3. **评审对事不对人。** 意见必须带位置和理由；"我觉得不好"不算意见，"这里直接返回了实体，泄漏了领域对象，建议改成 DTO"才算。
4. **不隐瞒阻塞。** 卡住超过半天必须在群里说出来，不允许"默默做别的"来掩盖进度落后。
5. **诚实标注未完成项。** 交付物只做了一半就写"完成 60%"，不写"已完成"。

## 三、沟通约定

### 3.1 会议节奏

| 会议 | 时间 | 时长 | 产出 |
| --- | --- | --- | --- |
| 每日站会 | 每工作日 21:30（线上） | ≤15 分钟 | 每人三句话：昨天做了什么、今天做什么、有无阻塞 |
| Sprint 计划会 | 每 Sprint 首日 | 60 分钟 | Sprint Backlog，任务拆到 ≤1 天粒度并分配到人 |
| 评审会（Review） | 每 Sprint 末日 | 30 分钟 | 可演示的增量 + PO 验收结论 |
| 回顾会（Retro） | 评审会后 | 30 分钟 | Start-Stop-Continue 三条改进项，落到下一个 Sprint |
| 技术讨论 | 按需，提前半天约 | ≤45 分钟 | 结论写成 ADR 或 Issue 评论，不留口头结论 |

### 3.2 沟通渠道与响应时限

| 渠道 | 用途 | 响应期望 |
| --- | --- | --- |
| 微信群 | 日常通知、站会、求助 | 工作时段 2 小时内 |
| GitHub Issue | 需求讨论、缺陷、技术债 | 24 小时内有人回复 |
| Pull Request 评论 | 代码评审 | 提交后 24 小时内给出首轮意见 |
| 仓库 `docs/` | 一切需要长期留存的决定 | 讨论有结论的当天必须落文档 |

**规则**：任何在聊天工具里达成的、会影响架构或需求的结论，必须在 24 小时内以 ADR 或 Issue 的形式落到仓库。只在群里说过的不算数——一旦口头约定没落文档，两端实现必然分叉。

### 3.3 信息同步

- 分支、Issue、PR 的命名必须能一眼看出属于哪个 Sprint、哪个需求编号。
- 每天的进度以 GitHub Projects 看板为准，不以群消息为准。
- 每周日 22:00 由 SM 汇总一次进度，贴在群里。

## 四、开发规约

### 4.1 分支模型

```
main                ← 随时可部署，已开启分支保护，禁止直接推送
feature/<描述>      ← 功能分支，从 main 切出，如 feature/qa-domain
docs/<描述>         ← 纯文档改动，如 docs/qa-error-codes
fix/<描述>          ← 缺陷修复
```

- 分支名统一小写，用连字符分词，如 `feature/12-question-vote`。
- **禁止直接向 `main` 推送**：`main` 已开启保护，必须走 PR 合并。
- 分支合并后即可删除；存活超过 3 天的分支要拆小或补中间提交。

### 4.2 提交信息

采用 Conventional Commits：

```
<type>(<scope>): <subject>

type:  feat | fix | docs | test | refactor | chore | perf
scope: identity | qa | reputation | discovery | shared | bootstrap | web | deploy | docs
```

示例：

- `feat(qa): 实现问题发布与标签校验`
- `test(reputation): 补悬赏过期结算的边界用例`
- `docs(adr): 新增包结构细则 ADR-009`

一次提交只做一件事。混着改需求和改格式的提交会被要求拆分。

### 4.3 代码规约

**后端**

- 依赖外置：跨上下文只能依赖对方的 `*-api` 模块或订阅事件，禁止直接 import 其他上下文的 domain / application 包。由 `ArchitectureTest` 的 FF-1~FF-6 强制。
- 领域层不出现框架注解（`@Entity`、`@Service`、`@Transactional` 一律不得出现在 `*-domain` 的模型类上）。
- 校验用共享内核的 `Guard`，不自己写 `if (x == null) throw ...`。
- 业务失败抛领域异常（`BusinessRuleException` / `ConflictException` / `ForbiddenException` / `NotFoundException`），**错误码必须取自 `docs/错误码.md`，不得自造段位**。
- 金额与积分用 `long`，禁止 `double`。
- 时间入参统一 `Instant`，由应用层注入，领域层不许调 `Instant.now()`。

**前端**

- TypeScript 严格模式，禁止 `any`；确实需要时写 `unknown` + 类型守卫。
- 接口类型集中在 `src/types.ts`，与 OpenAPI 契约对齐（ADR-007）。
- 组件不直接 `fetch`，统一走 `src/api.ts`。

**通用**

- 单个方法不超过 40 行，圈复杂度超过 10 必须拆分。
- 不留 `console.log`、`System.out.println`、注释掉的死代码。
- 新增公开方法必须有 Javadoc / TSDoc 说明业务意图，不复述签名。

### 4.4 测试规约

| 层级 | 工具 | 要求 |
| --- | --- | --- |
| 领域单元测试 | JUnit 5 | 每个聚合根的核心不变式必须有正反用例 |
| 应用层测试 | JUnit 5 + 内存 Fake 仓储 | 覆盖编排逻辑与跨聚合协作，不启 Spring 容器 |
| 架构测试 | ArchUnit | FF-1~FF-6 必须全绿 |
| 集成测试 | Testcontainers（MySQL + Redis） | 关键链路：提问→回答→采纳→声誉入账 |
| 前端 | 手动验收 + 类型检查 | `npm run typecheck` 零错误 |

覆盖率门禁：领域层行覆盖率 ≥70%，核心聚合（Question、ReputationAccount）≥90%。数字不达标不许合并。

## 五、Done 的定义（Definition of Done）

一个 Backlog 项只有同时满足以下全部条件，才能在看板上移到「Done」：

1. 代码已通过 PR 合并到 `main`，且 `main` 上的构建未被破坏。
2. 新增/修改的行为有对应测试，且 CI 全绿（编译、单元测试、架构测试、覆盖率门禁四项通过）。
3. 领域层覆盖率不低于 70%，未因新增代码拉低整体数字。
4. 至少 1 名非作者评审通过；评审意见全部已回复或已修改。
5. 无新增 TODO 注释；确需延后的写成 Issue 并标注 `tech-debt` 标签。
6. 涉及接口变更的，`docs/` 下的契约或错误码表同步更新。
7. 用户可见的功能，在 Sprint 评审会上现场演示通过。
8. 涉及配置或部署的，`deploy/` 下的文件与运维手册同步更新。

**不满足第 2、4 条的一律不算 Done**，即使功能"在我机器上是好的"。

## 六、违规与例外

- 绕过分支保护强推 `main` 的，当次提交回滚，并在回顾会上说明原因。
- 评审走过场（只回"LGTM"不提任何实质意见）的 PR 不计入评审工作量。
- 因课程安排或考试导致进度冲突，提前 3 天在群里说明，由 SM 调整 Sprint Backlog，不允许事后补理由。
- 本宪章的修改需 3 人以上同意，并在本文件顶部更新版本号与修订说明。
